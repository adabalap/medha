# Adding Medha's brief to a PWA

Five minutes per app. No SDK, no build step, no backend.

> **This is not Samsung's Now Brief.** That has no third-party API — its
> custom cards are authored by the user in Settings and generated by
> Samsung's own AI, with no field an app can write. This is **Medha's**
> brief: a home-screen widget Medha owns, which several paired apps write to
> at once. It is the one digest surface on the device that accepts
> third-party content. Full reasoning in [../docs/NOTIFICATIONS.md](../docs/NOTIFICATIONS.md).

---

## Which client do you want?

| Your app is | Use | Why |
|---|---|---|
| A static page / PWA served from an origin | [`medha-brief.js`](medha-brief.js) | Pairs a browser origin, runs in the page |
| A Python process on the same device (Flask, a service, a cron job) | [`medha_brief.py`](medha_brief.py) | No CORS, no pairing code, no preflight — none of that governs a non-browser |

**If your app has a server side, prefer the Python client**, even if it also
has a web UI. Two reasons:

1. The state worth showing — requests served, latency, whether a supervised
   service is still up — lives in the server process, not the browser.
2. A browser-only integration only updates the brief while someone has a tab
   open, which defeats the point of a home-screen widget.

A worked example for a runit-supervised Termux service is in
[`hg-agent-brief.py`](hg-agent-brief.py).

### Getting a token server-side

Not by pairing: pairing binds a token to a web **origin**, and a Python
process has none, so Medha refuses with `no_origin`. Instead:

> Medha → drawer → **API clients** → **Add client** → id `hg-agent`, tick
> **Post notifications** → copy the token.

A token made that way has no bound origin, so Medha applies no origin check
to it. Keep it out of the repo:

```sh
# ~/.config/hg_agent/env, sourced by the runit run script
export MEDHA_TOKEN=...
```

## Before you write any code (browser clients)

**1. Serve your app over http or https.** A `file://` page sends
`Origin: null`, which every sandboxed iframe on the device also sends, so
Medha will not bind a token to it. GitHub Pages is fine.

**2. Add the Medha widget to a home screen.** Once, by hand. Until it is
placed, your writes succeed and store correctly but nothing draws them —
and no API call can detect that, so it looks like your code is broken when
it isn't.

**3. You do not need a model loaded.** The brief and notifications work with
inference stopped. Only `/generate` and friends need a model, so don't gate
your integration on `health().modelLoaded`.

## Wire it up

Copy [`medha-brief.js`](medha-brief.js) into your app. One file, no
dependencies.

```js
import { Medha } from "./medha-brief.js";

const medha = new Medha({
  port: 8001,        // Medha's status card shows this
  appKey: "journal"  // only needed if one origin hosts several apps
});
```

### Pair, once

The user reads a six-digit code off Medha's screen — drawer → **Pair a web
app** → tick **Post notifications** → Create — and types it into your app.

```js
if (!medha.paired) {
  await medha.pair(codeTheUserTyped);   // "418 902" or "418902"
}
```

The token is kept in `localStorage` under your `appKey` and survives
reloads. It is **bound to the origin that paired it**: moved to another
origin it returns `origin_mismatch`, which is the point.

### Write your section

```js
await medha.postBrief([
  { title: "Standup at 10", text: "platform team" },
  { title: "Rent due",      text: "Friday" }
], { ttlSeconds: 6 * 60 * 60 });   // optional; 24h default
```

This **replaces your section only.** Other apps' sections are untouched —
you are stating your whole current contribution, not appending to a log.
An empty array withdraws yours, so clearing needs no second call.

The response reports what was **kept**, which can be fewer than you sent:

```js
const r = await medha.postBrief(items);
// { ok: true, items: 3, pageRows: 3, maxRows: 12 }
```

`pageRows` is how many the widget draws at a time; `maxRows` is how many the
brief holds in total. They are different numbers because the widget rotates.

### Notify

```js
await medha.notify({ id: "build", title: "Build finished", text: "main → green" });

// Ongoing + progress is what may reach the One UI 8 Now Bar:
await medha.notify({
  id: "sync", title: "Syncing", text: "412 of 900",
  ongoing: true, progressCurrent: 412, progressMax: 900
});
await medha.cancelNotification("sync");   // when it's done
```

`{ posted: false }` is **not** an error. The call worked and Android refused
it, which on API 33+ means the user has not granted **Medha** the
notification permission. Your own app's permission is irrelevant — Medha
posts it, not you. The `reason` field says so.

## How much to write, and how often

The brief is a glanceable surface, not a feed.

- **5 items per app, 80-character titles, 200-character text.** The client
  truncates and caps locally so you see it, rather than letting the server
  drop content silently.
- **8 apps, 12 rows total, 3 drawn at a time.** Rows fill round-robin, so
  posting five items does not push a quieter app off the widget — but it
  does mean your fifth line is four rotations away.
- **Sections expire**, 24h by default, 60s–7d via `ttlSeconds`. A card from
  Tuesday still sitting there on Friday is worse than no card.
- **`/notify` is rate limited**: 10 in a burst, 30 a minute, per app. Over
  that you get `429` with `Retry-After`, which the client surfaces in the
  error message. The brief is not rate limited — write it whenever your
  state changes.

Post your brief when your state changes, not on a timer. Nothing polls it.

## Errors worth handling

Every failure throws a `MedhaError` with a `code`:

| `code` | What happened |
|---|---|
| `not_paired` | No token yet. Show your pairing UI. |
| `unreachable` | Medha not running, wrong port, `file://`, or an old build with no PNA preflight. The message lists all of them. |
| `origin_mismatch` | Token paired from a different origin. Pair again. |
| `forbidden` | Paired without ticking **Post notifications**. Pair again. |
| `rate_limited` | `/notify` budget spent; honour `Retry-After`. |
| `no_pending_code`, `wrong_code`, `code_burned`, `code_expired` | Pairing problems — show the message as-is, it is written for the user. |

```js
try {
  await medha.postBrief(items);
} catch (e) {
  if (e.code === "not_paired") showPairingPrompt();
  else if (e.code === "forbidden") showRepairPrompt();
  else showBanner(e.message);   // already human-readable
}
```

## Two browser facts that will cost you an hour

**An HTTPS page calling `http://127.0.0.1` is not mixed content.** Both
`127.0.0.1` and `localhost` are "potentially trustworthy" origins per the
Secure Contexts spec, so browsers allow it. People expect this to be blocked
and it isn't.

**Private Network Access is the real gate.** Chrome treats a public page
calling a private address as crossing a boundary and sends a preflight.
Medha answers it — but only for an origin that has already paired, and only
from v0.9.0. Against an older build the fetch fails with a bare
`Failed to fetch`.
