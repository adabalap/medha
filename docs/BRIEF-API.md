# Brief API reference

For programmatic clients — hg_agent, daemons, scripts. Everything here is
read from the v0.11.5 source, not from memory; the constants are named so
you can check them yourself.

If you are integrating a **browser** app, read
[NOTIFICATIONS.md](NOTIFICATIONS.md) instead — it covers the six-digit
pairing flow, CORS and the browser rules that will cost you an hour. None
of that applies to a server-side client holding a token.

---

## What the brief is

A home-screen widget Medha owns, which **several paired clients write to at
once**. Each client owns a section; writing replaces only your own, never
anyone else's.

**It is not Samsung's Now Brief.** That has no third-party API — One UI 9's
custom cards are authored by the user in Settings and generated by Samsung's
own AI, with no field an app can write. `GET /notify/capabilities` reports
`"nowBrief": false` with a `nowBriefReason` saying exactly that, so nobody
goes hunting for a flag they got wrong. Medha's brief is the writable
equivalent.

---

## Before anything else

Every endpoint below needs a bearer token **and** the `notify` capability on
the client that token belongs to:

```
Authorization: Bearer <token>
```

Get the token from Medha's drawer → **Copy API token**. Without the `notify`
capability you get `403`, not `401` — the token is valid, it just is not
allowed on this surface.

Base URL is whatever port Medha reports; `http://127.0.0.1:8001` on the
current device.

## `PUT /widget/content` — write your section

```json
{
  "items": [
    {"title": "ICICI credit card", "text": "payment missed",
     "dueAt": 1762022400000, "kind": "bill"},
    {"title": "Tata Play recharge", "dueAt": 1763337600000, "kind": "bill"}
  ],
  "ttlSeconds": 7200
}
```

| Field | Required | Notes |
|---|---|---|
| `items[].title` | yes | ≤ 80 chars. **Blank titles are dropped silently** — the item vanishes, the request still succeeds |
| `items[].text` | no | ≤ 200 chars, defaults to `""` |
| `items[].link` | no | `http`/`https` only, ≤ 2000 chars, no whitespace or control characters. **An unsafe link is dropped and the item is kept** — one bad URL does not fail the post |
| `items[].dueAt` | no | Epoch **ms**. Medha derives the urgency band and the chip from it |
| `items[].kind` | no | `bill` `date` `event` `alert` `done` `note` — anything else is dropped, the item is kept |
| `ttlSeconds` | no | Default 24h. **Clamped server-side to 60s … 7 days**, silently |

Response:

```json
{"ok": true, "items": 2, "pageRows": 3, "maxRows": 12}
```

**`items` is what was stored, not what you sent.** If you post 5 and get
back 3, two had blank titles. v0.9.0 echoed the request size while quietly
rendering fewer, which left clients with no way to see the loss — don't
assume your post landed intact, read the number.

`pageRows` is how many lines are visible at once; `maxRows` is total
capacity across all clients. Both are reported because conflating them was
a bug: a client can honestly say "3 of your 7 showing" instead of guessing.

### Errors

| Condition | Status | Body `code` |
|---|---|---|
| More than 5 items | 400 | `bad_request` |
| A title over 80 chars | 400 | `bad_request` |
| A text over 200 chars | 400 | `bad_request` |
| Missing or unknown token | 401 | `unauthorized` |
| Token lacks `notify` | 403 | `forbidden` — message names the client and the capability |

### Send `dueAt`, not prose

This is the field that matters most, and the one worth changing your client for.

Before it existed, a client wrote the distance into `text` — `"overdue 10
days"` — and that string sat on the home screen for as long as the section
lived. It was observably wrong on a real device: a widget showing a
five-hour-old string still claiming "10 days", with no way to be right again
until the next post.

With `dueAt`, Medha computes the distance **at draw time, every time**:

| `dueAt` relative to now | `band` | `due` |
|---|---|---|
| 10 days ago | `overdue` | `10d over` |
| yesterday | `overdue` | `yesterday` |
| today | `soon` | `today` |
| tomorrow | `soon` | `tomorrow` |
| in 6 days | `soon` | `in 6d` |
| in 8 days | `later` | `in 8d` |

Two rules that are not obvious:

**Whole days, not elapsed time.** A bill due "17 Nov" arrives as local
midnight on the 17th. At 14:30 that afternoon an elapsed-millisecond
comparison calls it overdue — wrong, and alarming. The arithmetic works in
days because people do.

**"Today" is local.** The device's UTC offset is applied, and re-read per
request so a DST change doesn't leave a long-running server an hour out. In
Hyderabad at 02:00 it is still the previous day in UTC; without the offset
every date would read one day short, every night, between midnight and
05:30 — which is exactly when a daily brief regenerates.

A non-positive `dueAt` is dropped rather than stored: `0` is a real instant,
and taken literally it would paint the whole widget red.

## `GET /widget/content` — read it back

Returns **your own section**. An admin client sees every section, which is
what the bundled UI uses.

```json
{
  "pageRows": 3,
  "maxRows": 12,
  "contributors": 2,
  "overdue": 1,
  "kinds": ["bill", "date", "event", "alert", "done", "note"],
  "sections": [
    {
      "clientId": "hg-agent",
      "updatedAt": 1762800000000,
      "expiresAt": 1762886400000,
      "age": "4m",
      "items": [{"title": "...", "text": "...", "dueAt": 1762022400000,
                 "kind": "bill", "band": "overdue", "due": "10d over"}]
    }
  ]
}
```

`contributors` counts **all** sections on the device, not just yours — so
you can tell whether you are sharing the widget with three other apps or
have it to yourself, which changes how much you should post.

`age` is pre-formatted for display: `just now`, `7m`, `3h`, `2d`.

`band` and `due` are **derived**, not echoed — they are what Medha will
actually draw. Read them back to check a `dueAt` you got wrong by a
timezone, without reimplementing the rule. `overdue` counts across every
section, because the widget's header badge does.

A `link` appears in the response **only if it survived validation**. Compare
against what you sent to detect a dropped URL.

## `DELETE /widget/content` — remove your section

```json
{"cleared": true}
```

`false` means you had no section to clear. Not an error.

## Limits, all of them

| Limit | Value | Constant |
|---|---|---|
| Items per client | 5 | `BriefPolicy.MAX_ITEMS_PER_SECTION` |
| Title length | 80 | `MAX_BRIEF_TITLE` |
| Text length | 200 | `MAX_BRIEF_TEXT` |
| Link length | 2000 | `BriefJson.MAX_LINK_LENGTH` |
| Clients on the widget | 8 | `BriefPolicy.MAX_SECTIONS` |
| Rows visible at once | 3 | `BriefPolicy.PAGE_ROWS` |
| Total rows | 12 | `BriefPolicy.MAX_ROWS` |
| TTL default | 24h | `BriefPolicy.DEFAULT_TTL_MS` |
| TTL range | 60s … 7d | `MIN_TTL_MS` … `MAX_TTL_MS` |

**When a 9th client posts, the section with the oldest `updatedAt` is
evicted** — oldest, not newest, so a full widget keeps moving instead of
freezing. Post regularly and you keep your slot; go quiet for a day and you
may lose it.

## How it renders, and why that changes what you post

Two facts worth designing around.

**Rows are interleaved round-robin, one item per client per pass.** Every
app gets its first line before any app gets its second. So **your first item
is the one most likely to be seen**, and your fifth may never be. Order by
importance, not chronology.

Section-by-section rendering was the alternative, and it meant one app
posting five items filled the entire widget and every other app was
invisible — the exact failure the per-client split exists to prevent,
reintroduced at the drawing step.

**Within each pass, the most recently updated client goes first.** Sections
are ordered by `updatedAt` descending, so with two clients A (older) and B
(newer) posting three items each, the rows come out:

```
B1  A1  B2  A2  B3  A3
```

Posting refreshes your position as well as your content — which is another
reason to post on change rather than on a slow timer.

**Only 3 lines show at a time; the rest rotate** while the screen is on, at
a user-configurable interval (3s default). Tapping the widget opens the full
brief; tapping an individual line opens its `link` if it has one.

The practical consequence: a line that is always the same is wallpaper, and
wallpaper trains the eye to skip the whole surface — including the line that
mattered. Post **deltas and exceptions**, not a dashboard. A service that is
down is a line; one that is up is not.

## Notifications — a different surface

`POST /notify` interrupts the user. The brief does not. Use notifications
for something that needs a human **now**; use the brief for what is worth
knowing at a glance but never worth a buzz.

```json
{"id": "sync", "title": "Indexing failed", "text": "disk full",
 "ongoing": false, "silent": true,
 "progressCurrent": -1, "progressMax": -1}
```

| Field | Required | Notes |
|---|---|---|
| `title` | yes | ≤ 200 chars, must not be blank |
| `text` | no | ≤ 2000 chars |
| `id` | no | Defaults to `"default"`. Reusing an id **replaces** that notification |
| `ongoing` | no | Persistent, non-dismissable |
| `silent` | no | Defaults to `true` |
| `progressCurrent` / `progressMax` | no | `-1` disables the progress bar |
| `link` | no | http(s) URL opened on tap. Unsafe or custom-scheme links are **dropped and the notification still posts** |

Response:

```json
{"posted": true, "id": "sync", "tapOpens": "link", "link": "https://host/n/1"}
```

`tapOpens` is `"link"` or `"medha"` — which target the notification actually
got. A client cannot see that from the shade, and a silently dropped link is
the kind of thing that gets blamed on the wrong layer for an afternoon. When
a link was sent and refused, `linkDropped` says why.

### Making your own app receive the tap

Both tap surfaces — a brief row and a notification — resolve the same way:
`ACTION_VIEW` plus `CATEGORY_BROWSABLE`. Two consequences:

**Your intent filter must declare `BROWSABLE`.** A filter has to match every
category in the intent. Omit it and the filter silently does not match, the
link goes to the browser, and nothing anywhere reports an error.

```xml
<intent-filter android:autoVerify="true">
  <action android:name="android.intent.action.VIEW" />
  <category android:name="android.intent.category.DEFAULT" />
  <category android:name="android.intent.category.BROWSABLE" />
  <data android:scheme="https" android:host="your.host" />
</intent-filter>
```

**Custom schemes do not work.** `quicksilver://note/1` fails validation and
is dropped. Use an `https://` deep link with a verified App Link.

**`posted: false` is not a server error.** It almost always means the user
has not granted Medha the Android notification permission, and the response
says so in a `reason` field rather than leaving you to search your own code.

`POST /notify` is **rate limited** — it is the one endpoint where a client
makes the *device* do something and it is cheap to call. Over the limit you
get `429` with a `Retry-After` header in seconds. Everything else in Medha
is self-limiting because the model runs slowly.

`DELETE /notify/{id}` cancels one. `GET /notify/capabilities` reports what
this device can actually do:

```json
{"sdk": 36, "liveUpdates": true, "nowBarLikely": true,
 "notifications": true, "widget": true, "brief": true,
 "nowBrief": false,
 "nowBriefReason": "no public API; use /widget/content for Medha's own brief"}
```

Check `notifications` before relying on `POST /notify`. Check `brief` before
relying on the widget.

## A working client

[`samples/medha_brief.py`](../samples/medha_brief.py) — standard library
only, nothing to install under Termux. It wraps all of the above and
normalises the error shapes.

[`samples/hg-agent-brief.py`](../samples/hg-agent-brief.py) — a worked
example built on it, with opinions about *what* to post. Read it for the
editorial rule; copy `medha_brief.py` for the transport.

Minimal version, if you would rather not take the dependency:

```python
import json, urllib.request

def put_brief(items, ttl_seconds=None, base="http://127.0.0.1:8001", token=""):
    payload = {"items": items}
    if ttl_seconds is not None:
        payload["ttlSeconds"] = int(ttl_seconds)
    body = json.dumps(payload).encode()
    req = urllib.request.Request(
        f"{base}/widget/content", data=body, method="PUT",
        headers={"Authorization": f"Bearer {token}",
                 "Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=10) as r:
        return json.load(r)

# Read the stored count back -- it is not necessarily len(items).
r = put_brief([{"title": "3 services down", "text": "nginx, redis, postgres"}])
print(r["items"], "of", 1, "stored")
```

## Things that are easy to get wrong

- **Assuming `items` in the response equals what you sent.** It does not when
  a title was blank.
- **Posting a dashboard.** Five static lines are wallpaper. Post what changed.
- **Putting the important thing last.** Round-robin means item 1 is seen and
  item 5 often is not.
- **Using `POST /notify` for status.** It interrupts. The brief exists so you
  do not have to.
- **Retrying a 400 or 403.** Deterministic. Only retry `429` (honour
  `Retry-After`), `503`, and transport errors.
- **Expecting a non-http link to error.** It is dropped silently and the item
  is kept. Diff the response if you care.
- **Writing the due date into `text`.** It goes stale within hours. Send
  `dueAt` and let the chip be computed.
- **Sending `dueAt` in seconds.** It is milliseconds. Seconds puts every item
  in 1970, which reads as ~56 years overdue.
- **Putting a URL in `text` and expecting it to be tappable.** Android does
  not linkify notification body text. Send `link`.
- **Registering an intent filter without `BROWSABLE`.** It will not match,
  and the failure is completely silent.
